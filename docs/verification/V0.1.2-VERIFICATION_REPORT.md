## Implemented behavior

Camera discovery reads metadata without starting capture. The initial choice prefers an available built-in camera. Capture opens the selected stable device ID using Qt Multimedia in an isolated process, rather than assuming Qt and OpenCV camera numbers match. Refresh/reordering preserves that identity. A missing or changed selected device stops/errors; it never falls back to an iPhone, Mac camera or system default. Stop before selecting another device, then explicitly Start.

Network setup offers bounded user-clicked IPv4 ONVIF WS-Discovery and a manual device-service address. Profile lookup supports Media/Media2, WS-Security UsernameToken and HTTP Basic/Digest challenges. Use selected stream fills the main controls; only Start opens video. Direct RTSP/RTSPS/HTTP/HTTPS endpoints remain available. Credentials stay in memory and are excluded from source labels, errors and optional metadata. Setup workers support cancellation and safe parent shutdown. XML entities/wide-encoding bypasses, cross-server redirects, oversized/slow responses and timeouts have explicit handling. No subnet port scan, camera configuration write or cloud video upload is performed.

The default YOLO11n model retains its 80 COCO classes. Two optional Open Images models provide 601 raw classes, with 577 permitted object categories after excluding demographic/body-part and weapon outputs. Both have 16 safety/tool catalog labels. A category browser, model selector and safety/tool filter are connected to real inference. Model changes occur at the next fresh session while stopped; switching sources with the same model reuses loaded weights. Names are normalized while class IDs remain model-specific. FramePacket and optional SQLite session records include the model filename; existing databases migrate without discarding older rows.

## Expanded catalog quality — unresolved limitation

Weights are official Ultralytics assets, pinned locally by SHA256:

- YOLO11n: default lightweight COCO model; existing license and measurements preserved.
- YOLOv8n Open Images: 7,226,939 bytes, SHA256 `3851dfbf39ed2a076b1f39215cc22dba64eb5646f282bf964703785b0bed6a41`.
- YOLOv8s Open Images: 22,986,811 bytes, SHA256 `4663086e1b8edbc4202a9ec589b03195ed149ef8aa8beeb4b503e0e35ff1731a`. Its complete class mapping was checked against the shared catalog on load.

The initial seven selected helmet/wrench/goggles photos produced no correct expected-category match at confidence .25 and same-class IoU .5. Those failures remain in `safety-tools-initial-nano.json` and `safety-tools.json`. A 25-photo nano comparison also produced zero exact-label matches, with one generic helmet prediction overlapping an annotated bicycle helmet. The production detector reproduced that generic helmet at confidence .369 and IoU .925 across repeated still frames. This is not a specific bicycle-helmet-class success.

The larger model's 25-photo screening also missed many objects. A focused production detector check on an annotated ladder succeeded on both CPU and MPS: confidence about .521, IoU .645, with IDs assigned across four repeated still frames per backend. Repeated stills do not demonstrate moving-tool identity correctness. Screening and comparison outputs, including wrong classes and empty results, are retained. These deliberately selected examples are not an unbiased accuracy benchmark.

**Safety/tool recognition remains experimental and is labelled that way in the interface.** No reliable PPE-compliance assessment is delivered. Generic helmet, glove and boot labels do not establish protective rating or proper use. High-visibility vests, fire extinguishers, face identity and unsupported specialized hazards are not claimed. Broad catalog size must not be mistaken for dependable field recognition.

## Performance and remaining acceptance

FPS, latency, frame age and skipped-frame counts are actual measurements. Current native cold first inference reached about 5.35 seconds; library preparation took about 23–59 seconds in separate runs. Subsequent observed ONVIF inference samples ranged around 59–182 ms during these runs. Concurrent verification affected timings, so these are observations, not a sustained benchmark or fixed FPS promise. Earlier V0.1.1 one-minute camera results around 24 warm FPS belong to that historical run, not a guaranteed result for the new capture adapter or expanded models. All raw cold timings remain visible.

Core acceptance has executed evidence for launch/dark rendering, real video/model/person/bag inference, boxes/confidence/IDs, numerical moving-object tracking, Start/Stop, measured performance, CPU/MPS, unavailable-camera failure, optional metadata, source release, automated tests and local end-to-end inference. Startup and future module interfaces are documented. Hardware unplug/replug, iPhone full GUI inference at a time it is available, physical ONVIF/RTSP CCTV on the user's network, private-footage accuracy, moving bags/tools through occlusion and multi-hour thermal/memory behavior remain field acceptance gaps. No supplied physical CCTV endpoint was available to test.

No autonomous incident, owner-association, sensitive-person classification, facial recognition or V0.2 BAGWATCH logic is implemented. Network camera compatibility depends on reachable endpoints, codec/authentication and device configuration; Wi-Fi alone cannot make every proprietary cloud-only CCTV usable. See CAMERA_NETWORK_SETUP.md for precise on-device connection steps.
