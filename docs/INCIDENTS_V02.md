# V0.2 incident services

`TemporalEventEngine` consumes fresh specialized detector observations including empty analysed samples. It separates detection confidence from severity (1–4), associates by model ID/version, class and tracker ID or overlap, and emits uncertain OBSERVED, CANDIDATE and ALERTED incidents. Repeated media timestamps do not count as new samples. A missing/low-confidence analysed sample breaks an unconfirmed consecutive sequence. Session changes, backward seeks and explicit resets clear association and cooldown state. Multiple sources and tracks have bounded state. Tracking and suppression remain estimates; neither detection confidence nor a human verification implies criminal intent.

Temporal persistence and the maximum allowed gap are measured in source-video seconds. `alert_latency_ms` is the source-time interval from first observation to temporal confirmation. It excludes camera decoding, inference, mailbox delay and operator review; it must not be labelled total end-to-end alert latency. Throughput below the maximum-gap setting prevents confirmation by design. Severity defaults to 3 for visible firearms/fire and 2 for knife/smoke/GHS observations, independently of confidence. Camera-specific values override global thresholds and category severity only for explicitly configured fields.

`IncidentWorker` owns the engine and SQLite connection away from inference and UI threads. Its newest-sample mailbox holds one packet; its command queue holds at most 64 requests. Accepted review/delivery commands drain during orderly shutdown; camera frames are discarded then. Optional storage failure disables recording while visible incident events continue. A dropped sample may reduce temporal confirmation coverage.

Recording and snapshot capture are disabled by default and require runtime opt-in. The incident database is separate from historical V0.1 detection metadata. Human review is ALERTED → ACKNOWLEDGED → VERIFIED/DISMISSED → CLOSED; an ALERTED incident can also be dismissed directly. Automated observations cannot undo a human review. Reviews store the current local operating-system account, note and time. Authorized retention or explicit deletion removes owned referenced evidence and incident rows while retaining an audit tombstone until audit retention expires.

The current access boundary is the local macOS account: owner-only directories (0700), database/snapshots (0600), no separate multiuser login. Audit records cannot be edited through the application, but the database is not cryptographically tamper-proof against its owner. Snapshots have SHA256 integrity checks and limited size/count/age; no application-layer encryption is claimed. Filesystem unlink/SQLite secure_delete do not guarantee physical SSD secure erasure. Use appropriate device protection for any sensitive deployment. Retention is checked when the service/store is used, not by an always-running background service.

Local audio/desktop output is opt-in. `submitted` means a platform request was accepted, with presentation/hearing unverified. It is recorded as delivered=false with an explanatory detail. No emergency service, email or mobile recipient is contacted. External notification adapters return unavailable until an explicitly authorized integration is implemented.

The 52 synthetic-observation/real-SQLite regression tests validate service behavior, not model accuracy or field safety. `tools/verify_v02_local_audio.py` tests real local Qt tone output state; its output transitions do not prove that a person heard sound.

Operator Center diagnostics always show the current source state and monitoring flag. Retained timings, FPS, memory and model-health details are explicitly marked historical after Pause, Stop, EOF, reconnect or error. The live statistics cards clear while inference is inactive, even when the final video frame remains visible.
